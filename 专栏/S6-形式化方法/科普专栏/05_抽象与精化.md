# 抽象是把双刃剑——怎么保证"简化"没删掉要命的行为？

> **上期回顾**：上一期我们把"永远不会同时绿"写成了真正的公式（就是上期那条以 AG 打头的安全公式），电脑这才看得懂、查得动。可有个前提一直悬着：那个红绿灯模型，是我们从第 2 期就开始"抽象"出来的——从一团乱的真实系统里，只挑了几条要紧的规则。问题来了：你"挑着挑着"，会不会把真正的 bug 也一起挑掉了？这期就来聊建模里最见功力、也最容易翻车的一步：**抽象与精化**。

## 一、复习一下：模型是"删繁就简"得来的

第 2 期我们拿红绿灯打了个样：真实系统里，灯是 LED 还是灯泡、电压多少、杆子什么颜色、今天刮不刮风……无穷无尽；可要回答"车会不会撞"，我们只留了三句话——冲突方向不能同时绿、切换走全红缓冲、循环往复。其余全扔了。

这一步"扔"，行话就叫**抽象**（abstraction）。

**名-实对应**：抽象，就是——从一份具体的、细节爆炸的真实系统（或它的代码、它的设计图）里，抽掉那些"和我们要回答的问题无关"的细节，得到一份简化、精确的模型。它是建模的核心动作，没有抽象，模型就还是那团乱麻，电脑根本算不动。

但请记住一句话，它既是建模的精髓，也是建模的陷阱：**你每删掉一个细节，就冒一次"漏掉要命行为"的风险。**

## 二、抽象的坑：删着删着，把 bug 也删了

别以为这是危言耸听。来看一个被抽象"美化"过的红绿灯。

假设我们的模型只抽象了"灯色"，规则是"南北绿时东西必红"。模型检测跑完，电脑盖章："安全，永远不会撞车。"你很放心。

可真实的控制器里，还藏着两样东西模型压根没写：

- 一个**黄灯过渡**阶段——南北从绿变红时，有个瞬间黄灯亮、软件却还没锁死东西向，若此时东西向的控制器也恰好在切换，俩方向可能短暂"都以为自己能走"；
- 一个**传感器故障**——车检器偶尔误报"没车"，让系统跳过全红缓冲直接放行。

这两样，恰恰是真实事故最爱发生的样子。而我们的模型，因为把它们"抽象掉了"，永远看不到这些状态。于是出现一个要命的局面：

> 电脑说"模型安全"，真实系统却在现实里撞了车。

这就叫**漏报**（unsound，不保真）。抽象这把刀，削掉了噪声，也可能削掉了真相。第 2 期说的"抽象得对不对"，问的就是这件事。

用个生活比方：**地图和实景**。一张城市地图，为了让你看清路网，丢掉了每栋楼的颜色、每棵树的品种。这本没问题。可如果制图时手一滑，把一条真实的岔路给漏画了——你拿着这张"简化"的地图，按图走，就真能掉进沟里。地图越精简越清爽，但"漏画的那条"越可能要你的命。**抽象的干净程度，和"漏掉要命细节"的风险，是同一枚硬币的两面。**

## 三、怎么让抽象"可信"？第一条路：宁枉勿纵的"过近似"

那怎么办？难道为了不漏，就把所有细节都塞回模型？那又回到"算不动"的老路了。形式化方法给出了一条聪明的原则，叫**过近似**（over-approximation，也叫"sound abstraction"，保真抽象）：

> 我们做抽象时，故意让"模型能表现出来的所有行为"，**包住**真实系统能表现出来的所有行为。

换句话说，模型比真实系统"胆子更大、花样更多"——真实系统做不到的某些事儿，模型允许它发生。这样带来一个铁的好处：

> 只要在模型上证明"安全"，那么真实的、行为更少的系统，一定也安全。

因为模型把"可能性"放大了，连放大版都安全，原版当然更没毛病。**代价**只是偶尔"误报"——模型说有风险，真实其实没有，白紧张一下；但**绝不会漏报**——绝不会模型说安全、现实却出事。这就是"宁枉勿纵"。

把这件事写成一条关系（注意这是真正的数学关系，不是散文里的"相当于"）：

```
Behaviors(M_abstract) ⊇ Behaviors(System)
```

读作：抽象模型的行为集合，包含真实系统的行为集合。式子里的"包含号"，意思就是"包住"。这条式子，正是模型检测敢放心简化大系统的理论底气——它保证"简化"不会让你盲目乐观。

## 四、第二条路：精化——从"标准答案"一步步填出"实楼"

过近似是"从上往下抽"时保平安。还有另一条对称的路，叫**精化**（refinement），是"从下往上填"时保平安。

还记得第 1 期说的**规约**吗？规约是"标准答案"：系统必须怎样、禁止怎样。比如规约写"任何时候冲突方向不得同时绿"。但规约太抽象，不能直接跑。工程师得一步步把它变成能跑的代码：先落成状态机（第 2 期的红绿灯模型就算一步），再加数据结构和算法，最后写成具体程序。

**名-实对应**：精化，就是——从一份抽象规约出发，每加一层细节，都保证"新版本做的每一件事，都是老版本允许的；老版本满足的性质，新版本一个不落全满足"。于是越往下越具体，但"允许的行为"只会变窄、不会变宽。

还是拿盖楼打比方（这回用它讲"从抽象到具体"）：

- **概念图**：只说"这楼要有电梯、能抗八级风"——这是规约，最抽象；
- **施工图**：把电梯画成具体的井道和配重——它不能把"电梯"改成"爬梯"，因为那违反了概念图；
- **实楼**：按图施工出来——它更不能凭空加一处"没有消防通道"的设计。

每一步往下，都在概念图的"允许范围"里填东西，没有哪一步偷偷突破了上层。这就叫"实现精化了规约"。

把这条关系也写成式子：

```
Impl ⊑ Spec
```

读作：实现（Impl）精化（refines）规约（Spec）。式子里的"精化号"，意思就是"实现是规约更窄、更具体的那一版"。它的含义正是上一节那条的反面——实现的行为集合，是规约行为集合的子集（更窄、更具体），所以规约上成立的性质，实现上统统成立。

## 五、抽象和精化：一根绳子的两头

把这两节放一起看，你会发现它们是**同一件事的两个方向**：

- **抽象**：从具体系统往下抽，得到简化模型——担心"抽掉了要命的"；对策是过近似，让模型包住真实，宁枉勿纵。
- **精化**：从抽象规约往上填，得到具体实现——担心"填的时候突破了上层"；对策是每步保真，让实现始终落在规约的行为集合之内。

一个往下收，一个往上填，**两头对着把"真实系统"和"我们想要的标准"锁死**。建模保真度这条线，到第 5 期才算真正接上第 2 期的伏笔、也和第 1 期的"规约"闭环了。

回到两本译著：抽象与精化，正是《软件系统规约》（Specification of Software Systems）贯穿全书的主线之一——它一大半篇幅就在讲"怎么从抽象规约一步步精化出可靠实现"；而模型检测能放心地"先把大系统抽象小再查"，靠的也正是本节这条"包含式"的保真保证。

## 六、小结 & 下期预告

这期三句话收住：

1. 抽象是建模的核心动作，但**每删一个细节都冒漏掉要命行为的风险**——删着删着把 bug 也删了，就叫漏报；
2. 守住抽象的可信，靠**过近似**：让模型行为集合包住真实行为集合，宁枉勿纵、绝不大意；
3. 守住"从规约到实现"的可信，靠**精化**：每加一层细节都不突破上层（也就是实现精化规约），保证标准答案一步步落地不跑偏。

下期预告：抽象能简化，可现实里的系统实在太大——高铁信号、芯片、操作系统，状态数随部件指数暴涨，就算抽象过，电脑照样翻不动。这就引出形式化方法最硬核也最实用的难题：**状态爆炸**，以及救场的几招（符号化模型检测、偏序约减等）。这正好接上第 3 期埋的"状态爆炸"那个伏笔。
