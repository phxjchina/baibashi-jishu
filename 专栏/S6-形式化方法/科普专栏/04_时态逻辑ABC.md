# 把"永远""最终"写进公式——时态逻辑 ABC

> **上期回顾**：上一期我们看清了模型检测怎么干活——把红绿灯模型里所有状态走一遍，查"永远不会同时绿"成不成立，不成还能甩出反例。但有个前提一直含糊着：那句"永远不会同时绿"，到底是人话写的，电脑哪看得懂？这期就来补上这关键一环——**时态逻辑**（temporal logic），教你怎么把带"时间"的话，写成电脑不误解的公式。

## 一、为什么普通数学写不出"永远"

平时写数学，描述的是"某一个瞬间"的事实：A 大于 B、集合 X 包含 Y。可我们关心的很多性质，是关于**一串状态随时间流动**的："永远不会出错""请求迟早会被响应""下一步就进入缓冲"。这些说的是"时间里的顺序"，普通数学一句话说不清。

**名-实对应**：时态逻辑（temporal logic），就是——在普通逻辑（与、或、非、蕴含）之外，额外加了几个专门描述"时间怎么流"的**算子**（operator）的逻辑。有了它们，一句话就能钉死"在某个状态序列上，某事始终成立 / 最终成立 / 下一步成立"。

## 二、三个最该认识的算子（还用红绿灯）

先认识三个最常用的（符号、读法都在下面，用"性质"代表"某句话是否成立"）：

```
X 性质   下一步：下一个状态，该性质成立
G 性质   永远：每个未来状态，该性质都成立
F 性质   最终：将来某个状态，该性质成立
```

- **下一步（记作 X）**：比如描述"全红"——意思就是"下一个状态进入全红"，正好对应红绿灯切换时"先缓冲一下"那一步。
- **永远（记作 G）**：比如描述"南北和东西不同时绿"——意思就是"从今往后，每个状态里二者都不会同时绿"。**注意！这正是上期那条安全性质的精确写法**——人话"永远不会同时绿"，落到公式就是它。
- **最终（记作 F）**：比如描述"救援到达"——意思就是"将来总有一个时刻，救援到了"。这类"好事迟早发生"的性质，行话叫**活性**（liveness），和上期的"安全性"正好是一对。

再多提一个干活最多的——**直到（记作 U）**：性质一 一直成立，直到 性质二 成立的那一刻。比如"请求发出后，一直等待，直到被响应"，就可以用"等待 直到 响应"来表达。

## 三、线性还是分支？LTL 与 CTL（轻讲，不吓人）

为什么会有两种时态逻辑？因为"未来"长什么样，取决于系统有没有选择：红绿灯下一刻去全红还是去东西绿，是确定的；但一个带随机或并发的系统，下一步可能分出好几条岔路。

- **LTL（线性时态逻辑）**：把未来看成**一条**确定的时间线（系统实际跑出来的那条轨迹），在上面问"永远 / 最终…"。适合描述"真实发生的一条路"。
- **CTL（计算树逻辑）**：把未来看成**一棵树**（每个状态可能长出好几条可能的路），还能加两个量词：**A** 表示"所有路"，**E** 表示"存在一条路"。于是"所有路 + 永远"这一组合，表示"在**所有**可能的演化路上，**永远**都成立"——这正是模型检测里最严格、也最常用的安全保证。

回到红绿灯，最硬的安全保证，要写成这样一条公式：

```
AG ¬(NS ∧ EW)
```

这里 NS 代表南北向绿、EW 代表东西向绿。它的意思是："无论系统怎么演化、无论走到哪个状态，南北和东西都绝不会同时绿。"这就是把上期的"车不会撞"，从人话翻译成了电脑看得懂、查得动的精确公式。线性时态逻辑里相近的写法也能表达相似意思，二者的根本差别在于语义着眼点——线性的一条路，对比分支的一棵树：

```
G ¬(NS ∧ EW)
```

对应回底稿：这两类逻辑，正是《模型检测原理》第 3 章（LTL）和第 6 章（CTL）的主角——也就是第 1 期提到的那本书最核心的两章。

## 四、为什么这步绝不能省：性质写不准，查也白查

模型检测的本事，一半在"自动穷举查"，一半在"性质写得多准"。性质一旦写错——把"永远"写成"最终"，或者漏了某个要命的状态——电脑查得再快，查的也是个错的。

时态逻辑，就是那座把"人话性质"翻译成"电脑不误解的精确公式"的桥。它也正是第 1 期说的**规约**真正落地的关键一步：规约里那句"必须…禁止…"，最终要落成这样的公式，模型检测才跑得起来。

红绿灯收尾：从"车不会撞"（人话），到上面那条 AG 公式（公式），电脑这才看得懂、查得动。

## 五、小结 & 下期预告

这期三句话收住：

1. **时态逻辑**就是：给逻辑加"时间算子"，能说清"永远 / 最终 / 下一步"；
2. 三个核心算子是 **X**（下一步）、**G**（永远）、**F**（最终），CTL 再补上 **A**（所有路）/ **E**（存在一条路）；
3. 性质写进公式，电脑才看得懂——这是模型检测能跑起来的前提。

下期预告：模型有了、性质也写成公式了，可别忘了——**模型是从代码 / 设计里"抽象"出来的**。这步抽象怎么保证没漏掉要命的行为？这就引出**抽象与精化**（abstraction & refinement），建模里最见功力、也最容易翻车的一步。它正好接上第 2 期埋的"抽象得对不对"那个伏笔。
