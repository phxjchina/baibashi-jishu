# 先写下你要什么，再让机器算

## ——规格、Event‑B 与 UPPAAL 各自在干什么活

> 形式化方法专栏（S6）· 第 3 篇
> 全文约 3300 字

---

## 一、一个我们都被骗过的时刻

你有没有过这种时刻？

需求文档上写着"用户登录失败三次后锁定账号"。你照着写了，测过了，交上去了。上线第二天，有人报告：换个浏览器重新打开页面，输错三次，账号没锁。

对方说的完全符合需求文档。你也完全符合需求文档。

**然后你们两个人都是对的，但产品是错的。**

这不是谁偷懒。这是自然语言本身的毛病——**"锁定账号"这件事，你没说清是锁"这个账号"，还是锁"这个设备上的这个账号"；你没说清锁定时间是十分钟、二十四小时，还是永久。**这些话在你脑子里是清楚的，因为它在你脑子里不是一个词，是一整块经验。

形式化方法要解决的，就是这一类"你脑子里清楚但纸上没写清"的东西。它不是要你写得更好听，是要逼你**写得能被机器读懂**。

前面两篇讲清了"为什么要做"和"为什么测试不够"。这一篇讲**具体做的时候，三个角色各自负责哪一段**——它们经常被混为一谈：

| 角色 | 回答的问题 | 一句话 |
| --- | --- | --- |
| **规格（Specification）** | 我们要什么？ | 写下来的**期望** |
| **模型（Model）** | 系统长什么样？ | 系统所有可能的**行为** |
| **验证（Verification）** | 会不会出问题？ | 机械地找**反例** |

很多文章把"验证"当成形式化方法的全部，好像形式化方法就是那个查 bug 的工具。**这只是最后一步，而且是最容易被跳过的一步。**前两步才是它真正的分量。

## 二、规格：先把"应该怎么做"写清楚

先给"规格"这个名词找个实。

它的现实对应物是**装修合同**。

装修房子的时候，业主和装修公司之间那份东西，才是关键。不是"我要一个客厅"，而是"客厅长 4.2 米、宽 3.6 米、地板型号 X、插座位置距墙 300 毫米"。

**为什么必须是数字，不能是"差不多就行"？**

因为验收的时候，"差不多"没法验。**规格的作用不是指导施工，而是提供一个可以判定的基准。**谁都可以争，但只要基准写下来了，争执就结束了一半。

形式化规格是同一件事，只不过它判定的对象不是米和毫米，是"状态"和"事件"。

### 自然语言规格的三个先天病

这一节要说的不是我的抱怨，是有出处的分析。Alagar & Periyasamy 的教材（*Specification of Software Systems*, 2nd ed., Springer, 2011）在 §1.2.6 给了一个很锋利的二分——**噪声（noise）与沉默（silence）**，它引的是 Meyer 的分析。

**病一：噪声（noise）。** 用**不同的词**指称**同一个概念**。

书中实例：`"nonempty sequence" of items` 和 `"one or more" items`——**这两个是同一件事**，但读的人不知道。

Meyer 给技术文档定的规则是：**同一个概念必须用同一个词表达。**这里有个反直觉的地方——**文学写作要避免重复，而技术写作相反：技术写作必须重复。**同一个概念反复出现，是准确；换个说法，才是问题。

**病二：沉默（silence）。** 文本中**未定义的概念**，以及**已定义概念之未定义特征**。

书中两个实例：
- "event a happens after event b" —— **happens 和 after 都可被不止一种方式解释**；
- "an identifier can have **up to** eight characters" —— **"up to" 本身就是歧义**（是最多 8 个，还是不超过 8 就可以是 0 个？）

**病三：图也无救。** 这一条最容易被忽略。"非形式的描述，诸如图表，**除非配有精确的注解，否则没有内在语义**。"画得再漂亮的时序图，箭头指向哪、什么时候，都得靠注解补上。

**根本判断（原文）**："自然语言表达力强但不精确。**任何软件性质都能用自然语言表达**，但那个表达可能被赋予不同的解释，或者**根本无法被理解**。"

（配套的证据在教材的练习题里，很有意思：第 1 题让你用自然语言描述两个文本编辑器，然后**数一数有多少条 Meyer 式缺陷**；第 2 题让你拿**菜谱**做同一件事——"bake the cookies"这五个字里，隐含了多少环境假设？烤箱温度？几分钟？多少个？烤糊了怎么办？**这些问题一个都没写在菜谱上，但每一个都会让你烤糊。**）

三个病的共同点：**它们都不是"理解错了"，而是"根本没写"——或者写的时候，用的词和脑子里的词不是同一个。**所以再认真的团队也会踩。

### 一个必须分清的概念：验证 vs 确认

这里有个最常被追问的问题，答案在两个词里：

**形式化方法能不能保证"需求本身是对的"？**

不能。教材里有一组标准的区分（Baier & Katoen, p.12，引 Boehm）：

| | **验证（Verification）** | **确认（Validation）** |
| --- | --- | --- |
| 检查什么 | 设计是否满足**已识别**的要求 | 形式模型是否符合**非形式的设计构想** |
| 常用说法 | **"我们是不是在正确地造这个东西"** | **"我们验证的是不是正确的那个东西"** |

**这个区分很要紧**：形式化方法保证的是"你写下来的东西被正确地实现了"，它**不**保证"你写下来的东西是对的"。后者是需求工程的事，不在形式化的能力范围里。

但也别因此低估它——**在你把脑子里的东西变成白纸黑字的过程中，形式化会替你挡掉一部分错**。上一节那三个病里的"冲突"（比如"1 秒内响应"和"三级审批每级至少留一个工作日"），就是机器能替你发现的：**当它们被写成可判定的形式，那个矛盾就藏不住了。**

### 但请给自然语言一个公道

这里必须说句公道话，因为科普文章最容易把它说偏。

**自然语言写规格不是"错的做法"，只是精度到不了。**

ISO、IETF、IEEE 那些协议规范——HTTP、TCP、蓝牙、BGP——由全球最会抠字眼的一群人打磨出来，人类完全读得懂，也完全能用。**你去查 RFC 791（TCP），里面全是自然语言，没有任何一行公式，它依然精确到了可以据此实现互操作的操作系统。**

那问题出在哪？出在**自然语言精确到"可以实现"，但精确不到"可以机械对照"**。

> **一句话**：自然语言足够用来**沟通**，不够用来**判定**。形式化要补的就是"可判定"这一格。

## 三、状态机：把"东西变成什么样"写清楚

光有期望还不够——你还得说清系统长什么样，这就是**模型**。

而形式化方法里最基础的一种模型，是**状态机**。这个名字听起来玄，其实日常得很。

它的现实对应物是**医院病房的灯**：

- **状态**：亮 / 灭。
- **事件**：有人按了按钮。
- **迁移**：从亮变灭，或者从灭变亮。

复杂的医院病房还有"呼叫中"、"护士已响应"、"超时未响应（红灯闪）"。这就是一台状态机。

**一台状态机只有三样东西，请记住这三个词——后面两篇全靠它：**

| 名词 | 英文 | 在医院灯里是什么 |
| --- | --- | --- |
| **状态** | State | 灯是亮还是灭 |
| **迁移** | Transition | 从亮变灭这一步 |
| **事件** | Event | 有人按了按钮 |

而状态机真正厉害的地方，是它能回答两类完全不同的问题：

**问题一（只关于过去）：灯现在是什么状态？**
这只要看"当前状态"就够了。

**问题二（关于未来）：我按了按钮，灯什么时候会灭？会不会永远亮着？**
这需要"迁移关系"。而一旦你说"永远"——这就是性质了。

**状态机把"系统"变成了"状态 + 迁移 + 事件"这三个可以严格定义的词。**这一步是所有后续工具的地基：Event‑B 的机器、UPPAAL 的位置和边，都是它的变体。

### 不变式：状态机里最值钱的一句话

在状态机上，有一种句子特别值钱，叫**不变式**（invariant）——**它说：一个条件在每一个可达状态下都成立。**

"不变式"这四个字翻译得不好。原意是：**一件东西，在整个过程的每一步，都保持同一个值。**

打个日常的比方。一间教室有 60 把椅子，上课下课换了一茬又一茬的学生——有人进来，有人出去，有人在外面站着。但只要"这间教室坐得下这届学生"这个安排没被人动过，**椅子的数量永远是 60**。

那 60 就是这间教室的不变式。**进来的每一步、出去的每一步，都必须保住它。**谁要是搬走一把椅子，条件就被破坏了——而这件事，跟今天上了几节课、来了多少人，**一点关系都没有**。

这句话要跟第一篇讲的一样，说准：

> **不变式不是"初始的时候成立"，而是——它在初始状态成立，并且被每一个事件保持；因此，它对系统的每一个可达状态都成立。**

注意它的强度：不是"我启动时检查了一下，通过了就往下走"，而是"**从第一秒到最后一秒，任何一个瞬间被看一眼，它都得是真的**"。

### 一个必须澄清的常见误解

很多人以为"不变式"就是"初始状态要满足的条件"。**不是。**这里有两条完全不同的义务：

1. **INITIALISATION**：初始状态必须满足这个不变式；
2. **INV（保持性）**：每个事件执行完之后，新状态**还**必须满足这个不变式。

只有两条都成立，不变式才真的对所有可达状态成立。**少任何一条，它就退化成一个"开局检查"，跟测试没有本质区别。**

## 四、性质：分两类，难度天差地别

模型上要看的那些句子，叫**性质**（property）。性质分两大类，这个分类是整个领域的骨架。

用打比方来说最省事：

| | **安全性（Safety）** | **活性（Liveness）** |
| --- | --- | --- |
| 现实对应 | **食品安全** | **上菜速度** |
| 承诺什么 | 吃了不会中毒，**永远不会**出事 | 你点了菜，**最终一定会**上来 |
| 时间要求 | 不带时间 | 往往带时间 |
| 逻辑写法 | `A[] p`（沿**所有**路径**始终** p） | `A<> p`（沿**所有**路径**最终** p） |

这个分类里有一个**最容易被忽略、也最该记住**的点：

> **安全性只承诺"坏事不发生"，它不承诺"好事会发生"。**

把它翻译成软件。一台完全符合规格的坏电梯：楼层显示、按钮响应、门开闭逻辑全部正确，**但门开着的时候，不会有任何人来把它关上**。只要这条"关门"的活性没写进规格，电梯就是一个完美的合规产品——**它不会有坏事发生（安全性全过），但它也不好用。**

活性难得多，因为它要求"最终"，而**"最终"没有时间上界，你没法穷举到头。**这个技术难题在第六节会直接兑现。

## 五、Event‑B：不写"程序怎么做"，只写"数据永远是什么样"

到这里，"形式化方法"还悬在半空。真正把它变成可执行手艺的，是一套叫 **Event‑B** 的方法。

它的思路值得单独说，因为这是形式化方法的一个根本转向：

> **不问"程序应该怎么做"，而是问"数据必须永远是什么样"。**

程序怎么写，那是程序员的事；机器只负责盯那句话。

先认一下人。**Jean‑Raymond Abrial** 这位法国科学家，1970 年代末在 Grenoble 提出了一套语言叫 Z（Zulu），后在牛津继续发展，标准编号 ISO/IEC 13568:2002——他是主要发起者之一，不是唯一发明者。1990 年代他基于 Z 发展出 B 方法（1996 年的 *The B‑Book* 是这条线的权威文本）。再往后，为了对付分布式系统里"事件"这件在 Z 里不好安放的事，B 演化成了 **Event‑B**：把"状态"和"改变状态的事件"彻底分开。

用医院病房灯做个对照，一眼就懂 Event‑B 的结构：

| 医院灯 | Event‑B |
| --- | --- |
| 灯亮 / 灯灭 | `VARIABLE 状态`（状态住在**机器**里） |
| "按按钮"这个动作 | `EVENT`（事件住在**事件**里） |
| 按钮在哪个灯亮着才有效 | `WHERE`（守卫 guard） |
| 按下之后灯怎么变 | `THEN`（动作 action） |
| **"任何时候不可能又亮又灭"** | `INVARIANT`（不变式） |

**注意最后一行：不变式不是一句注释，它是 Event‑B 里的正式字段。**

一套最小的 Event‑B 长这样（**伪代码，展示结构，不是可运行代码**）：

```
MACHINE 咖啡机
VARIABLES  水量, 状态
INVARIANT  水量 >= 0                    ← 不变式，永远为真的那句话
           / 状态 ∈ {"就绪","煮中"}
EVENT 就绪时启动煮咖啡
  WHERE   水量 > 0                      ← GRD（守卫）：允许发生的前提
  THEN    状态 := "煮中" , 水量 := 水量 - 1   ← ACT（动作）：实际改了什么
EVENT 煮完
  THEN    状态 := "就绪"
```

现在看 `水量 >= 0` 是怎么被守住的：

- 初始水量 100，满足 ≥ 0；
- "启动煮咖啡"这个事件，守卫是 `水量 > 0`，所以它**只有在水量至少为 1 时才能发生**；发生之后水量减 1，变成 ≥ 0。**还是非负。**
- "煮完"不改水量。

所以不管你摁多少次按钮，水量永远不会变成负数——**而这不是我们测出来的，是一句逻辑推出来的。**回到第一篇那个答辩现场：学生缺的那句"从哪来的、会不会变坏"，在这里被写成了两行字，并且可以交给机器验。

### Rodin：把守不变式的活儿交给机器

手算这个太累。于是有了 **Rodin**。

Rodin 是欧盟第七框架计划项目 IST‑511599（2004–2007，ETH Zurich，Abrial 团队）的产物，全称 *Rigorous Open Development Environment for Complex Systems*。它是**开源软件**（EPL 许可），基于 Eclipse，最初由法国公司 Systerel 领导维护，2025 年后转由 IRIT 与 CentraleSupélec 维护。本工作区里就躺着 rodin‑3.5.0 的安装包和 rodin‑3.5 展开目录——**是个真实的 Eclipse 应用。**

Rodin 干的第一件事，是**把"那句永远为真"自动拆成一堆证明义务**（Proof Obligation，简称 PO）。所谓证明义务，通俗说就是"要证明这句话，你一共得先回答这几个具体问题"：

| PO 类型 | 它在问什么（人话） |
| --- | --- |
| INV | 事件执行完，不变式还成立吗？ |
| FIS | 有没有哪个变量，从此再也不被任何事件改动？ |
| GRD | 这个事件会不会永远被守卫拦住、动不了？ |
| SIM | 不同事件会不会同时想改同一个变量、打起来？ |
| NAT | 这个变量会不会溢出或者跑成负数？ |
| FIN | 这个变量会不会永远等不到初值？ |
| WFIS | 有没有"什么都没发生"的死水状态？ |
| WD | 每个事件是不是真的至少能被触发一次？ |

**有件事必须说清楚：这些证明义务里，有相当一部分机器能自动证完，也有相当一部分证不完，需要人来想。**

网上常见"Rodin 自动证明 99%"的说法——**这个数字请不要引用。**我们核查到的实测数据里，学术小模型案例的自动化率从 23% 到 86% 都有，差异极大，取决于模型里有多少数组、多少复杂算术。工业界那个流传很广的"99%"追到源头只是一篇 2012 年会议论文的二手转述，没核到原文。**诚实的说法是：Rodin 消掉的是"机械劳动"，不是"全部劳动"。**

那人工的部分在干什么？举一个经典例子：你要证"事件后集合 S 的大小不变"。S 是什么？会不会有重复元素？它是数组还是关系？——**每答错一个问题，这条 PO 就证不过去。**

而这恰恰是它最有价值的地方：**它把你心里含糊的地方，逼成一句白纸黑字的话。**这就是第二节那三个病（歧义、缺失、冲突）的解药——**不是让你写得更详细，是让你写完能被打分。**

**B 方法的工业史**是这句话最好的背书，而且有硬数据。国内形式化方法的老前辈裘宗燕老师（北京大学数学学院）在她 2010 年的《基于 B 方法的软件开发》讲义里，给出了两个项目的完整账单：

| 项目 | 投入规模 | 产出 | 交互式证明占比 | 人月 |
| --- | --- | --- | --- | --- |
| **巴黎地铁 14 号线**自动驾驶系统（**1998 投运**） | 8.5 公里 / 8 站 / 列车间距 115 秒 / 40 km/h / 17 列车 / 每天旅客 350000 | **ADA 代码 86000 行，证明定理 27800 个** | **8.1%** | 7.1 人月 |
| **巴黎 Roissy 机场自动穿梭车**（2006 投运） | 3.3 公里 / 5 站 / 105 秒 / 26 km/h / 14 列车 / 每小时 2000 人 | **ADA 代码 158000 行，定理 43610 个** | **3.3%** | 4.6 人月 |

请留意"交互式证明占 8.1%"这一栏——**这就是"机器能自动证 92%"的第一手工业级证据**，比网上流传的"99%"可信得多，也朴素得多。它同时也说明另一件事：**剩下那 8% 才是人的工作，而那 8% 恰恰是最需要 expertise 的地方。**

历史更早的名单也很长：**IBM CICS** 系统更新用 Z 语言做再工程（见《Using Z》）；**法国 GEC‑ALSTHOM Transport** 用 B 方法开发法国高速铁路控制系统，成为形式化开发的典范；90 年代 Moore 等受 AMD 委托证明了 **AMD K5 浮点除法运算的正确性**；**基于形式化模型的程序分析工具在 Windows 2000 的源代码中找出了数以万计的错误和漏洞**；连规范本身也在用——**RBAC 2004 规范用 Z 描述，W3C 的 WSDL 2.0 规范（2005）也用 Z**。

（数据出处：裘宗燕 2010 年讲义。**注意**：巴黎 14 号线用的是**经典 B（classical B）**，不是后来才有的 Event‑B，这两个名字在文献里常被混着说，这里先掰开。14 号线的一手论文是 Behm 等 1999 年 FMIFS 的 *METEOR: A successful application of B in a large project*。）

> **一句话记住 Event‑B：不写"程序应该怎么做"，而是写"数据必须永远是什么样"，然后让机器证明每一次改动都没弄坏这句话。**

## 六、UPPAAL：给"永远"和"最终"装上秒表

上面那些性质，还不涉及时间。但很多系统偏偏就是**和时间较劲**：电梯 30 秒内必须到、列车不能在同一轨道区间相撞、心跳包 500 毫秒内必须来一次、协议超时必须是 200 毫秒而不是"永远等"。

第四节说过，这类"多久之内必须"的性质，是活性里的硬骨头——**"最终"没有上界，人就没法穷举**。

**时间自动机**（Timed Automata）就是为这件事造出来的：**Rajeev Alur 和 David L. Dill** 在 1991 年的 *Theoretical Computer Science* 第 160 卷第 2 期发表 *A Theory of Timed Automata*（Alur 也在 1991 年 8 月完成同名博士论文，导师 Dill 与 Manna）。这篇至今是开山之作。

它对普通状态机的改造非常克制：**状态机的边上，不再只写"条件成立就走"，而是写"条件成立，且距离上次事件已经过了 5 毫秒，才走"。**就加这么一个"计时器"，能力就变了——**它能问"最多等多久"。**

**UPPAAL** 是把这件事做成能用的工具的那一步。它 1995 年首次发布，作者名单是 Johan Bengtsson、Kim G. Larsen、Fredrik Larsson、Paul Pettersson 和 Wang Yi（**这里更正一个流传的错误：网上常见的"UPPAAL 由 Bengt Jonsson 开发"是错的，Bengtsson 和 Jonsson 是两个人**）。今天由丹麦 Aalborg 大学的 DEIS 组维护分发。**它不是开源软件**：学术非商业用途免费，但要去注册学术 license key；商业授权要付费，协议明确禁止分发和改源码。版本上今天已进到 **UPPAAL 5.0**，看到有人说"UPPAAL 4.x"，那是历史版本。

它的模型就是一台带秒表的自动机：**闹钟**（clock）、**变量**（int）、**事件**（动作，带守卫和时间约束）、**位置**（状态）。你拖出一台电梯的图形，问它"乘客从 3 楼按了按钮，最长多少秒能到"，它就在状态空间里穷举，替你数。

用的性质语言叫 **Timed CTL（定时 CTL）**，是 CTL 的有限子集：

- 安全性：`A[] p` —— 沿**所有**路径**始终** p（官方文档叫 invariantly）
- 活性：`A<> p` —— 沿**所有**路径**最终** p（叫 eventually）
- 会导致：`p --> q` —— "p 会导致 q"，展开是 `A[](p ⇒ A q)`

那"最多 10 秒"怎么写？**这里有个值得记住的细节：UPPAAL 官方文档并不提供 `P<=3U<=5 Q` 这种区间 until 公式。**官方做法是把"带截止时间的活性"**归约成一条安全性性质**——写成 `A[] (b imply z <= t)`：从 b 发生那一刻起，计时变量 z 必须在 t 以内到达目标值。

**换句话说，"10 秒内必须发生"在 UPPAAL 里是当成一条"永远别超时"的安全性质来查的。**把关于"未来"的问题，改写成关于"每一刻"的问题——**这跟第三节不变式的精神是同一个招数，而它正是可验证性的通用手法之一。**

**UPPAAL 真用过的地方**（均查得到一手出处）：

- **Bang & Olufsen**（丹麦音响设备商）：音视频协议见 RTSS 1997，UPPAAL 自动找出了常规测试没发现的错误；电源开关协议见 AMAST 1999，是在**实现之前**验证了 15 条性质。
- **Philips** 音频协议（LPW95b, 1995；BGKLLPW96, CAV 1996）；**ABB** 商用现场总线协议。
- **Mecel AB** 车辆变速箱控制器：TACAS 1998，自动证明 46 条性质。
- **LEGO MINDSTORMS RCX**。
- **铁路**：丹麦理工（DTU）的 Jan Peleska 等用 UPPAAL 验证了丹麦真实的分布式联锁系统（RELIS 2000 / Nærumbanen）；Basile 等在 FMICS 2019（LNCS 11687）用统计模型检查分析 ERTMS / ETCS Level 3 移动闭塞信号；Alstom 在 VALU3S 项目中用 UPPAAL 验证铁路信号 SIL4 控制器的时间性质。

顺便清两条讹传：**"UPPAAL 在 European Computer Research Center（ECR）做铁路验证"查无可靠出处；"UPPAAL 验证过 Volvo"同样查不到。**

## 七、收束

**这一篇请你带走的五句话：**

1. **规格、模型、验证是三件事。**验证只是最后一步，却是经常被跳过的一步——**前两步才是形式化方法的真正分量。**
2. **规格是装修合同，不是"我想要个客厅"。**它的作用不是指导，而是提供一个**可以判定的基准**。自然语言足够用来沟通，不够用来判定。
3. **自然语言规格的三个病：歧义、缺失、冲突。**它们的共同点不是"理解错"，而是"根本没写"——所以再认真的团队也会踩。
4. **不变式不是"开局检查"，是"每一步都得守住"。**初始成立，还要被每个事件保持，这才是"永远"。
5. **UPPAAL 给"永远"和"最终"加上了秒表**，手法是把"10 秒内必须发生"改写成"任何时刻都不许超时"：**把关于未来的问题，改写成关于每一刻的问题。**

**思维工具（带走的三句人话）：**

- 需求评审时，问一句：**"这句话如果由两个不同的人来实现，会不会做出两个不同的产品？"**会，就还没写清。这比"写得清不清楚"有用得多。
- 写完一条性质，接着问一句：**"这条性质会被破坏吗？如果会，在哪一步？"**答不上来，说明这条性质没有信息量。
- 自己评估一个系统时，把它想成一间教室，问一句：**椅子的数量，会不会被谁偷偷搬走一把？**答不上来，那这就是一个还没写下来的不变式，也是一个没人守的承诺。

**下次你在哪能看见它：**翻开任何一份航空机载项目的适航文档，或任何一份电梯 / 列车 / PLC 的安全需求表，找"不变量"那一栏——你会发现工程师写的东西，和"椅子必须永远是 60 把"是同一种句子，只是把椅子换成了油门开度、刹车压力、报文长度。**这门手艺，就在这儿。**
