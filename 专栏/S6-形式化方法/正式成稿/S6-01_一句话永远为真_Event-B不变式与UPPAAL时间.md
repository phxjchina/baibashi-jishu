# 一句话永远为真

## ——从"菜谱到底写清楚了没有"，到 Event‑B 的不变式和 UPPAAL 里的时间

> 形式化方法专栏（S6）· 启动篇
> 全文约 3800 字，建议分 3 次推进（①② / ③④⑤ / ⑥⑦⑧）

---

## 一、先讲一个我们都会遇到的难堪

我们学院某届学生的毕业设计，功能全做出来了，演示那天跑得很顺。答辩时，一位老师问："你这个登录功能，怎么保证用户输错三次密码之后就被锁住？"

学生打开代码，指着屏幕上那行 `if (count >= 3) lock();` 说："这里判断了呀。"

老师没说话，笑了笑，走了。

我们没发火，是因为**我们自己也说不出哪里不对**。代码明明写了那个判断，我们凭什么说它可能不对？

憋了半天，晚饭时候我们想明白了，这事儿之所以说不清，是因为这段代码只回答了一个问题：**"系统现在处于什么状态。"**

它没回答另外三个：

- 这个状态**是从哪来的**？（初始对不对）
- 这个状态**以后会不会变坏**？（演化中会不会被破坏）
- 这套行为**是不是我们一开始想要的**？（想要的东西有没有被写下来）

代码天然擅长描述"现在"。而工程上我们真正花钱买的，恰恰是另外三件。

## 二、形式化方法到底是什么：给一段程序找毛病的一门手艺

先破一个误会。**"形式化方法"这四个字听起来像一门外语课，其实它指一门非常朴素的手艺——找毛病。**

给它一个现实里的对应物：**餐厅过敏原登记。**

一家饭店要保证"每位客人知道自己吃的是什么"，正规做法是在菜谱上把每道菜的**全部成分**登记在册，包括那些"绝对想不到会放"的：酱油里的小麦、泡打粉里的小麦、汤底里的花生、辣椒油里的芝麻。客人问服务员，服务员翻菜谱，一分钟给出准确答案。**不许服务员"凭印象"回答"应该不含吧"。**

形式化方法干的就是这件事，只不过对象不是菜谱，是程序。核心只有三步：

| 一步 | 在现实里是 | 在形式化里是 |
| --- | --- | --- |
| 1. 把"应该怎么做"写清楚 | 菜谱上登记成分，缺项补齐 | **规格**（Specification）：先写下期望的性质 |
| 2. 穷举所有可能的情况 | 后厨逐道菜过一遍锅 | **模型**：系统所有可能的运行 |
| 3. 机械地对照，找出不合适的那一个 | 主管查过敏原表对客人 | **验证**：用逻辑推理找反例 |

请注意第 3 步里的"机械地"。这是这门手艺和"多测试几遍"的**根本分界线**：

> **测试是抽查。形式化验证是全称。**

你测一千次都没出错，只能说明这一千次没问题；形式化验证说"这条性质对**所有**可达状态成立"，那才是"所有"。这个区别，就是我们付钱给形式化方法行业的全部理由。

这条路在学术上不是新 inventions。1981 年，Edmund Clarke（后来拿图灵奖）和 Edsger Emerson 在卡内基梅隆，Yannick Quielle 和 Joseph Sifakis 在法国，各自独立搞出来一套办法：**不运行程序，而是把系统所有可能的行为穷举一遍，逐条检查你关心的那条性质是不是一直成立。**这个办法叫**模型检查**（Model Checking），它是形式化方法这一门里最"暴力"、也最容易被初学者接受的一支。

它的强大和它的软肋是同一件事：**它穷举所有情况。**

## 三、为什么"写清楚"这么难：规格的三个先天病

第一步"把应该怎么做写清楚"，是整条链上最容易被人低估、也最容易翻车的一步。

按名—实对应的法子先给"规格"这个名词找个实：**它就是那份菜谱。**它不是代码，也不是设计文档，它是一份**用来对照的清单**——上面写的不是"怎么做"，而是"做完之后什么东西必须成立"。

问题在于，自然语言写的规格天生带三个病。我们用一个学生请假系统的例子说，三病都齐：

**病一：歧义。** 需求写"离校需经辅导员审批"。那么，"辅导员"是括辅导员、行政秘书，还是分管学生工作的老师？只有一句"辅导员"三个字，两个班一个行政秘书一个副书记，这条需求就至少有两种实现方式，而且**两种都算实现了需求**。到出事的那天，才发现没人知道该谁批。

**病二：缺失。** 需求说"请假超过三天需要院长批准"，但**没说三天是"连续"还是"累计"**。学生说"我这个月请了三次，每次一天，加起来三天"——批还是不批？需求里根本没有这个信息，两种答案都合理，**bug 已经存在了，只是还没显形。**

**病三：冲突。** 一份需求说"离校系统应在 1 秒内响应"，另一份说"所有离校申请须三级审批，每级至少停留 1 个工作日以便复核"。两条都没错，放在一起，1 秒响应这件事**在物理上就不可能**。

这三个病的共同点是：**它们都不是"理解错了"，而是"根本没写"。**所以再认真的开发团队也会踩。形式化方法解决不了"你压根没想清楚要什么"，但它能**逼你把想清楚的东西写下来，并且检查你有没有自相矛盾**——这已经是巨大的进步了。

值得说一句公道话：自然语言写规格不是"错的做法"，只是"精度到不了"。ISO、IETF 那些由全球最会抠字眼的一群人打磨出来的协议规范，人类完全读得懂，也完全能用。**形式化不是要取代自然语言，而是要补上自然语言天生缺的那一格：精确。**

## 四、性质分两类：坏事别发生，和好事终会发生

规格上写下来的那些"必须成立"，叫**性质**（property）。性质分两大类，这个分类是整个领域的骨架，先立住了，后面所有工具都好懂。

拿餐厅打比方：

- **安全性（Safety）**：**食品安全**。吃了不会中毒——不管你点什么菜、点多少次，**永远不会**出事。它承诺的是"坏事永不发生"。
- **活性（Liveness）**：**上菜速度**。你点了菜，**最终一定会**上来——哪怕慢。它承诺的是"好事终会发生"。

这一章的分量差别，是本专栏里最容易被忽略、也最该记住的一点：

> **安全性只承诺"坏事不发生"，它**不承诺**"好事会发生"。**

把它翻译成软件。一台完全符合规格的坏电梯：楼层显示、按钮响应、门开闭逻辑全部正确，**但门开着的时候，不会有任何人来把它关上**——只要这条"关门"的活性没写进规格，电梯就是一个完美的合规产品。它不会有"坏事"发生（安全性全过），但它也不"好用"。

活性难得多，因为它要求"最终"，而**"最终"没有时间上界，你没法穷举到头**。这一点在第六节 UPPAAL 那里会直接兑现成一个具体的技术难题。

## 五、不变式：把"永远为真"这句话写下来

现在我们把第四节的"永远"，落成一句可以交给机器的话。

"Invariant"这个词，中文一般译成**不变式**、**不变性**或**恒真式**，翻译都不算好，因为它把原意压扁了。原意是：**一件东西，在整个过程的每一步，都保持同一个值。**

打个日常的比方。一间教室有 60 把椅子，上课下课换了一茬又一茬的学生——有人进来，有人出去，有人在外面站着。但只要"这间教室坐得下这届学生"这个安排没被人动过，**椅子的数量永远是 60**。

那 60 就是这间教室的不变式。进来的每一步、出去的每一步，都必须保住它。谁要是搬走一把椅子，条件就被破坏了——**这件事故，跟今天上了几节课、来了多少人，一点关系都没有。**

换成软件：

| 教室 | 软件 |
| --- | --- |
| 椅子 = 系统当前的数据 | **状态**（State） |
| 学生进出 = 改变状态的那一刻 | **事件**（Event） |
| 椅子数永远是 60 | **不变式**（Invariant） |

所以"不变式"的准确含义不是"初始的时候成立"，而是——

> **它在初始状态成立，并且被每一个事件保持；因此，它对系统的每一个可达状态都成立。**

这句话是本文的地基。**请注意它的强度：不是"我启动时检查了一下，通过了就往下走"，而是"从第一秒到最后一秒，任何一个瞬间被看一眼，它都得是真的"。**

### 一个必须澄清的常见误解

很多人（包括不少刚入门的学生）以为"不变式"就是"初始状态要满足的条件"。不是。这里有两条**完全不同的义务**：

1. **INITIALISATION**：初始状态必须满足这个不变式；
2. **INV（保持性）**：每个事件执行完之后，新状态**还**必须满足这个不变式。

只有两条都成立，不变式才真的对**所有**可达状态成立。少任何一条，它就退化成一个"开局检查"，跟测试没有本质区别。

这个"从满足不变式的状态出发，经过任何一个操作，结果得到的状态是否仍然满足不变式"的判准，是国内形式化方法教材里给出的最简洁表述（裘宗燕《形式化方法：基于 B 方法的软件开发》，北京大学，2010）。它道出了不变式为什么必须每步都守住——**只有守住一步，才能守住所有步。**

Event‑B 里更完整的版本是循环：**WHILE 条件 DO 动作 INVARIANT I VARIANT V END**。注意这一行里有两样东西：**条件与动作说的是"做什么"，I 与 V 说的是"凭什么说它对"。**任何程序都要同时提供这两条轨——这本身就是形式化最本质的思想。而 V（变动量）还多问一句：V 必须每次迭代都减小，这保证了循环**会停**。

## 六、落到 Event‑B：不写程序，写"必须永远是什么样"

到这里，"形式化方法"还悬在半空。真正把它变成可执行手艺的，是一套叫 **Event‑B** 的方法。

它的思路值得单独说一句，因为它是形式化方法的一个根本转向：

> **不问"程序应该怎么做"，而是问"数据必须永远是什么样"。**

程序怎么写，那是程序员的事；机器只负责盯那句话。

先认一下人。**Jean‑Raymond Abrial** 这位法国科学家，1970 年代末在 Grenoble 提出了一套语言叫 Z（Zulu），后在牛津继续发展，标准编号 ISO/IEC 13568:2002——他是主要发起者之一，不是唯一发明者。1990 年代，他基于 Z 发展出 B 方法（1996 年的 *The B‑Book* 是这条线的权威文本）。再往后，为了对付分布式系统里"事件"这件在 Z 里不好安放的事，B 演化成了 **Event‑B**：把"状态"和"改变状态的事件"彻底分开。

一套最小的 Event‑B 长这样（**伪代码，展示结构，不是可运行代码**）：

```
MACHINE 咖啡机
VARIABLES  水量, 状态
INVARIANT  水量 >= 0                    ← 不变式，永远为真的那句话
           / 状态 ∈ {"就绪","煮中"}
EVENT 就绪时启动煮咖啡
  WHERE   水量 > 0                      ← GRD（守卫）：允许发生的前提
  THEN    状态 := "煮中" , 水量 := 水量 - 1   ← ACT（动作）：实际改了什么
EVENT 煮完
  THEN    状态 := "就绪"
```

现在看 `水量 >= 0` 是怎么被守住的：

- 初始水量 100，满足 ≥ 0；
- "启动煮咖啡"这个事件，守卫是 `水量 > 0`，所以它**只有在水量至少为 1 时才能发生**；发生之后水量减 1，变成 ≥ 0。**还是非负。**
- "煮完"不改水量。

所以不管你摁多少次按钮，水量永远不会变成负数——**而这不是我们测出来的，是一句逻辑推出来的。**回到第一节那个答辩现场：学生缺的那句"从哪来的、会不会变坏"，在这里被写成了两行字，并且被机器验过了。

### Rodin：把守不变式的活儿交给机器

手算这个太累。于是有了 **Rodin**。

Rodin 是欧盟第七框架计划项目 IST‑511599（2004–2007，ETH Zurich，Abrial 团队）的产物，全称 *Rigorous Open Development Environment for Complex Systems*（面向复杂系统的严格开放开发环境）。它是**开源软件**（EPL 许可），基于 Eclipse，最初由法国公司 Systerel 领导维护，2025 年后转由 IRIT 与 CentraleSupélec 维护。本工作区里就躺着 rodin‑3.5.0 的安装包和 rodin‑3.5 展开目录——**是个真实的 Eclipse 应用，不是传说。**

Rodin 干的第一件事，是**把"那句永远为真"自动拆成一堆证明义务**（Proof Obligation，简称 PO）。所谓证明义务，通俗说就是"要证明这句话，你一共得先回答这几个具体问题"：

| PO 类型 | 它在问什么（人话） |
| --- | --- |
| INV | 事件执行完，不变式还成立吗？ |
| FIS | 有没有哪个变量，从此再也不被任何事件改动？ |
| GRD | 这个事件会不会永远被守卫拦住、动不了？ |
| SIM | 不同事件会不会同时想改同一个变量、打起来？ |
| NAT | 这个变量会不会溢出或者跑成负数？ |
| FIN | 这个变量会不会永远等不到初值？ |
| WFIS | 有没有"什么都没发生"的死水状态？ |
| WD | 每个事件是不是真的至少能被触发一次？ |

有件事必须说清楚：**Rodin 自动生成的证明义务里，有相当一部分机器能自动证完，也有相当一部分证不完，需要人来想。**

网上常见"Rodin 自动证明 99%"的说法——**这个数字请不要引用。**我们核查到的实测数据里，学术小模型案例的自动化率从 23% 到 86% 都有，差异极大，取决于模型里有多少数组、多少复杂算术。工业界那个流传很广的"99%"追到源头只是一篇 2012 年会议论文的二手转述，我们没能核到原文。**诚实的说法是：Rodin 消掉的是"机械劳动"，不是"全部劳动"。**

那人工的部分在干什么？举一个经典例子：你要证"事件后集合 S 的大小不变"。S 是什么？会不会有重复元素？它是数组还是关系？——**每答错一个问题，这条 PO 就证不过去。**

而这恰恰是它最有价值的地方：**它把你心里含糊的地方，逼成一句白纸黑字的话。**这就是第三节那三个病（歧义、缺失、冲突）的解药——不是让你写得更详细，是让你**写完能被打分**。

B 方法的工业史是这句话最好的背书。1998 年投运的**巴黎地铁 14 号线**（METEOR），由 Matra（后并入 Siemens Transportation）为 RATP 开发，列车运行、停车、车门与站台门这些安全攸死的软件，用 B 方法从抽象模型一路走到 Ada 代码自动生成——**注意：14 号线用的是经典 B（classical B），不是后来才有的 Event‑B，这两个名字在文献里常被混着说，这里先掰开。**一手出处是 1999 年 FMIFS 的 *METEOR: A successful application of B in a large project*（Behm 等）。往后还有：纽约 Canarsie 线的 CBTC（Siemens Transportation）、Alstom 的 URBALIS 400（2014，墨西哥/多伦多/圣保罗/巴拿马）、Roissy‑Charles‑de‑Gaulle 机场线的 CDGVAL（2007，Siemens 与 CLEARSY）。综述可查 ACM *Formal Aspects of Computing* 的 "A History of Formal Methods in Railways" 及 Krings 等人 HFM 2019 / FMICS 2020。

> **一句话记住 Event‑B：不写"程序应该怎么做"，而是写"数据必须永远是什么样"，然后让机器证明每一次改动都没弄坏这句话。**

## 七、落到 UPPAAL：给"永远"和"最终"装上秒表

上面两节已经能处理餐厅食品安全那类问题了。但很多系统偏偏就是**和时间较劲**：电梯 30 秒内必须到、列车不能在同一轨道区间相撞、心跳包 500 毫秒内必须来一次、协议超时必须是 200 毫秒而不是"永远等"。

第四节说过，这类"多久之内必须"的性质，是活性里的硬骨头。**时间自动机**（Timed Automata）就是为这件事造出来的：**Rajeev Alur 和 David L. Dill** 在 1991 年的 *Theoretical Computer Science* 第 160 卷第 2 期发表 *A Theory of Timed Automata*（Alur 也在 1991 年 8 月完成同名博士论文，导师 Dill 与 Manna）。这篇至今是开山之作。

它对普通状态机的改造非常克制：**状态机的边上，不再只写"条件成立就走"，而是写"条件成立，且距离上次事件已经过了 5 毫秒，才走"。**就加这么一个"计时器"，能力就变了——它能问"最多等多久"。

**UPPAAL** 是把这件事做成能用的工具的那一步。它 1995 年首次发布，作者名单是 Johan Bengtsson、Kim G. Larsen、Fredrik Larsson、Paul Pettersson 和 Wang Yi（**这里更正一个流传的错误：网上常见的"UPPAAL 由 Bengt Jonsson 开发"是错的，Bengtsson 和 Jonsson 是两个人。**）。今天由丹麦 Aalborg 大学的 DEIS 组维护分发。**它不是开源软件**：学术非商业用途免费，但要去注册学术 license key；商业授权要付费，协议明确禁止分发和改源码。版本上今天已进到 **UPPAAL 5.0**，所以看到有人说"UPPAAL 4.x"，那是历史版本。

模型就是一台带秒表的自动机：**闹钟**（clock）、**变量**（int）、**事件**（动作，带守卫和时间约束）、**位置**（状态）。你拖出一台电梯的图形，问它"乘客从 3 楼按了按钮，最长多少秒能到"，它就在状态空间里穷举，替你数。

它用的性质语言叫 **Timed CTL（定时 CTL）**，是 CTL 的有限子集：

- 安全性：`A[] p` —— 沿**所有**路径**始终** p（官方文档叫 invariantly）
- 活性：`A<> p` —— 沿**所有**路径**最终** p（叫 eventually）
- 会导致：`p --> q` —— 读作"p 会导致 q"，展开是 `A[](p ⇒ A q)`：p 一发生，q 必须跟着发生

那"最多 10 秒"怎么写？**这里有个值得记住的细节：UPPAAL 官方文档并不提供 `P<=3U<=5 Q` 这种区间 until 公式。**官方做法是把"带截止时间的活性"**归约成一条安全性性质**——写成 `A[] (b imply z <= t)`：从 b 发生那一刻起，计时变量 z 必须在 t 以内到达目标值。

**换句话说，"10 秒内必须发生"在 UPPAAL 里是当成一条"永远别超时"的安全性质来查的。**把关于"未来"的问题，改写成关于"每一刻"的问题——这跟第五节不变式的精神是同一个招数，**而它正是可验证性的通用手法之一**。

### UPPAAL 真用过的地方

不是玩具。查得到一手出处的：

- **Bang & Olufsen**（丹麦音响设备商）：音视频协议见 RTSS 1997，UPPAAL 自动找出了常规测试没发现的错误；电源开关协议见 AMAST 1999，是在**实现之前**验证了 15 条性质。
- **Philips** 音频协议（LPW95b, 1995；BGKLLPW96, CAV 1996）；**ABB** 商用现场总线协议。
- **Mecel AB** 车辆变速箱控制器：TACAS 1998，自动证明 46 条性质。
- **LEGO MINDSTORMS RCX**。
- **铁路**：丹麦理工（DTU）的 Jan Peleska 等用 UPPAAL 验证了丹麦真实的分布式联锁系统（RELIS 2000 / Nærumbanen）；Basile 等在 FMICS 2019（LNCS 11687）用统计模型检查分析 ERTMS / ETCS Level 3 移动闭塞信号；Alstom 在 VALU3S 项目中用 UPPAAL 验证铁路信号 SIL4 控制器的时间性质。

顺便清两条讹传：**"UPPAAL 在 European Computer Research Center（ECR）做铁路验证"查无可靠出处；"UPPAAL 验证过 Volvo"同样查不到。**一手的铁路案例就是上面那三条，引用时用它们。

## 八、它也会卡住、也会冤枉人

如果这么灵，为什么它没替代所有测试？

**第一，它会卡住。** 这不是工具的懒，是问题的规模：**穷举法天生怕指数。**

先看一个真实协议里的数字。**交替位协议**（alternating bit protocol，一个最简单的可靠传输协议）在模型检查的教科书里被反复用作状态爆炸的标本：**它的状态数是 3 × 2³⁵，约一千亿。**

而这只是个只有三个变量的小协议。

权威教材把门槛说得很具体（Baier & Katoen, *Principles of Model Checking*, p.8）：**目前最先进的模型检查器，用显式状态空间枚举，能处理大约 10⁸ 到 10⁹ 个状态**；用精巧的算法和定制的数据结构，**特定问题**上可以做到 10²⁰ 甚至 10⁴⁷⁶ 个状态。

**"一千亿"和"十亿"之间，差着三个数量级。**这就是"模型检查器在你的笔记本上转三天"的原因。

那为什么偏偏是指数？裘宗燕老师的讲义里有一句话点破了根源：**"大量实现细节大大增加了程序的复杂度，从而极大地提高了分析和推理的成本（通常不是规模的线性函数，可能是指数的）。"**换句话说——**爆炸不是因为变量多，是因为你把不该记的细节也记进了模型。怎么把模型写小，本身就是一门手艺。**

（这类问题的经典归属我们核查后无法给出可靠一手文献，所以只讲现象，不安人名。）

**第二，它会冤枉人。** UPPAAL 为了对付爆炸会做抽象，官方文档写得很直白：状态空间表示可选"**过近似**"（Over Approximation，用 convex‑hull zone 近似），此时"UPPAAL 可能得出一个查询*也许*被满足/违反的结论，找到的反例轨迹**可能是虚假的（spurious），即不可实现的**"。

翻译成人话：**抽象就是"宁可多算，不可漏算"——它会把现实中不可能发生的情况也算进去。**这保证了"不漏"（没有真 bug 被藏起来），代价是"多报"（凭空冒出假 bug）。

生活里的对应物是**一场找错的抽奖活动**：主办方为省事，把某些肯定不符合条件的号码也塞进了奖池。结果抽出一个"中奖者"，一核对发现根本不符规则——**白忙一场，还得跟所有人生气。**

所以你会在 UPPAAL 文档里看到 `spurious` 这个词。看到它，就知道：**这个 bug 未必是真，但你也不能直接当假的忽略掉**，你得回去把模型改精确一点，让它露出来。**模型写得粗糙，机器就只能给你一个粗糙的答案。**

**第三，时间本身有个数学坑。** 想象一个门口，每 0 秒挤进一个人，人越来越多但都挤在门外那一小块地方。1 秒之内能挤进无穷多个人吗？数学上能，这叫 **Zeno 执行**——有限时间内发生无限多步。

理论上 Zeno 行为**可以判定**（已被证明）。但在 UPPAAL 实际采用的 LU‑extrapolation 技术下，**Zeno 判定的复杂度是 NP‑完全的**（Herbreteau & Srivathsan, CONCUR 2011）——翻译：**极贵**。文档里另一句相关的话是：**即使你显式选了更精确的 DBM 表示，只要模型里用了 stopwatch，过近似依然会发生。**想精确，代价更高。

> **一句话记住这一节：形式化验证不是"算给你看"，是"在你承受得起的精度内，算给你看"。精度和成本，永远是一对需要权衡的孪生兄弟。**

这里可以把话说得更诚实一点。权威教材对这个局限的判断是（Baier & Katoen, p.16）：**"我们相信，对现实规模的系统，绝对保证的正确性永远不可能达到。"**但它紧接着说：**"模型检查是一种有效的技术，用来暴露潜在的设计错误。它能为系统设计的信心水平带来显著的提升。"**

两句要一起读。**不保证零缺陷，但显著提高信心——这才是这门手艺真实的承诺。**任何跟你说"用了形式化方法就绝不会出 bug"的人，都在夸大。

而整本教材里最该被记住的一句，其实出现在第 8 页：

> **"任何基于模型的验证，都只能好到模型那么好。"**

模型写得粗糙，机器就只能给你一个粗糙的答案。**这一点和上一节那句"假反例可能是虚假的"是同一件事的两面。**

## 九、收束

**这九节请你带走的五句话：**

1. **形式化方法就是"给菜谱登记过敏原"——把该写清楚的写清楚，再机械地对一遍。**它的分界线是：**测试是抽查，验证是全称。**
2. **规格天生带三个病：歧义、缺失、冲突。**形式化治不了"你压根没想清楚"，但能逼你**写完能被打分**。
3. **性质分两类：安全性和活性。安全性只承诺"坏事不发生"，它不承诺"好事会发生"。**活性难得多，因为"最终"没有上界。
4. **不变式不是"开局检查"，是"每一步都得守住"**——初始成立，还要被每个事件保持，这才是"永远"。
5. **UPPAAL 给"永远"和"最终"加上了秒表**，手法是把"10 秒内必须发生"改写成"任何时刻都不许超时"：**把关于未来的问题，改写成关于每一刻的问题。**

**思维工具（带走的三句人话）：**

- 听到有人说"我们加了断言/加了检查"，追问一句：**这个检查是初始态做的，还是每一步都做的？**这一句就能问出真假。
- 看到一份"我们做了形式化验证"的报告，追问：**验的是安全性的（坏事别发生）还是活性的（好事终会发生）？**只验前者，通常说明交付压力不小。
- 自己评估一个系统时，把它想成一间教室，问一句：**椅子的数量，会不会被谁偷偷搬走一把？**答不上来，那这就是一个还没写下来的不变式，也是一个没人守的承诺。

**下次你在哪能看见它：**下次翻开任何航空机载项目的适航文档，或任何一份电梯 / 列车 / PLC 的安全需求表，找"不变量"那一栏——你会发现工程师写的东西，和"椅子必须永远是 60 把"是同一种句子，只是把椅子换成了油门开度、刹车压力、报文长度。**这门手艺，就在这儿。**
