# Webhook：让 Broker"主动给你打电话"

## 一、我当年的困惑

讲个真事，我学生时代自认为通透的那个晚上。

平台跑起来了： EMQ X 收消息， Node.js 后端处理，一切正常。我正得意，旁边的师兄问了一句：

" Broker 收到新消息，你的后端是怎么知道的？"

我说："定时去问啊，每隔一会儿查一次。"

师兄没说话，看了我一眼。那一眼我记到今天——**不是鄙视，是"原来你不知道自己不知道"。**

后来读付强的书，第 11 章专门讲这个事，我才明白那一眼的分量。这一篇，就讲这件"小事"：**设备的数据到了 Broker，后端怎么第一时间知道？** 以及，为什么说这个问题是"玩具平台"和"真平台"的分水岭。

## 二、两种知道的方式：打电话问，还是等电话来

先建立一个谁都秒懂的类比。

**方式一：轮询（ Polling ）——打电话问。**

后端每隔 200 毫秒给 Broker 打一个电话："有新消息吗？""有吗？""现在呢？"

感觉一下： Broker 就是那个物业前台，你是个偏执的业主，一天打 432000 个电话过去问"我的快递到了吗"。前台啥正事别干了。你也累——大部分电话的答案是"没有"。

**方式二： Webhook——等电话来。**

你跟前台说："快递一到，**你打我电话**，别等我问。"

从此世界安静了。没快递，相安无事；快递一到，前台主动呼你，电话里还带着快递单号。

Webhook 这个词， hook 是"钩子"的意思。**前端在 Broker 身上挂了个钩子，指定一件事：某事发生，就顺着钩子呼我这个网址。** 在物联网里，这个"呼"就是一个 HTTP 请求—— Broker 把设备上线、设备发布消息这些事件， POST 到后端的一个 URL 上，后端在该来的地方等着收。

EMQ X 自带一个 WebHook 插件，付强书里的 IotHub 早期就用它： Broker 把事件 POST 给 Node.js 后端，后端开始处理。

到这儿，故事听起来完美了。

## 三、但付强泼了三盆冷水

如果文章停在这儿，就是个happy ending 的技术童话。付强厉害的地方，是他把生产环境的冷水一盆盆端上来。他列举了 WebHook 插件的三个问题，我念给学生听的时候，全班安静。

**第一盆：身份存疑。** Broker POST 给后端时，不带任何身份凭证。后端傻了：**我咋知道呼我的真是 EMQ X，不是隔壁老王在捣乱？** 陌生人打电话说"你快递到了"，你也得核个实吧？

**第二盆：性能浪费。** 更扎心的是——你只关心"设备发消息"，可 Broker 连"设备订阅了主题""消息已送达"这些你根本不感兴趣的事件，也一个一个 POST 给你。等于前台连"今天天气晴"都要给你打电话。每一次 POST 都是一次完整的 HTTP 开销：建连接、发数据、关连接。**不关心的事，也照呼不误。**

**第三盆：丢消息。** 假设后端服务宕机了半小时。这半小时里 Broker 该呼你的电话，全部打不通——**数据就丢了。** 修复上线后，你永远不知道那半小时错过了什么。

三盆冷水泼完，结论很清楚：**自带的 WebHook 插件，做演示可以，上生产，差点意思。**

## 四、自己造钩子：emqx-rabbitmq-hook

怎么办？付强的选择很硬核：**自己写插件。**

EMQ X 的架构留了口子——它内部定义了一大堆 Hook 点（设备连接、断开、发布消息……），开发者可以写插件，在这些点上挂自己的处理函数。插件得用 Erlang 写（因为 EMQ X 就是 Erlang 写的，近水楼台）。

于是有了 `emqx-rabbitmq-hook` 这个插件，名字就说明了一切： **EMQ X 的钩子 + RabbitMQ 的队列。** 它把三盆冷水一一接住：

**接住身份问题**：消息不进 Web 接口了，进 RabbitMQ。RabbitMQ 有完整的认证和 ACL——想往我的邮局投信，先报户名口令。身份，有了。

**接住性能问题**：插件可配置！哪个事件呼我、哪个不呼，配置文件里开关一打。只挂 `client.connected`（设备上线）、`client.disconnected`（下线）、`message.publish`（发消息）这三个钩子，其余免谈。

**接住丢消息问题**：这是最妙的一手——事件进了 RabbitMQ 的**持久化队列**。哪怕后端全宕了，消息也在队列里躺着，**后端重启，从断点接着取，一条不丢。**

插件的工作流，白话讲就三步：

1. 设备一上线， EMQ X 内部 `client.connected` 钩子被触发；
2. 插件把事件数据（设备 ID、用户名、 IP、上线时间……）编码成 BSON，投进名为 `mqtt.events` 的交换机；
3. 后端的 Node.js 从绑定的队列里把消息取走，该更新 MongoDB 更新 MongoDB，该写 InfluxDB 写 InfluxDB。

**从"打电话"变成"寄挂号信，邮局签收，丢不了。"** 这就是生产级的回调。

## 五、邮局 RabbitMQ：为什么是它

可能有同学问：存个消息而已，用数据库存不行吗，非得上 RabbitMQ？

行，但 RabbitMQ 是专业的。它是用 Erlang 写的 AMQP Broker——对，跟 EMQ X 同门，都是电信血统。它专治三种病：

- **异步**： Broker 呼后端这一下，不必等后端处理完。投进队列就走，后端慢慢取。**寄信的人不需要等收信人拆信。**
- **削峰**：半夜一万台设备同时上报，后端处理不过来？队列先攒着，后端按自己的节奏消化。**洪水来了，水库先蓄着。**
- **可靠**：队列可持久化，支持确认应答（后端说"这条我处理完了"才删除）。**挂号信，签收才算完。**

你们发现没有——物业公司里，门房（ EMQ X ）管"设备进出"，邮局（ RabbitMQ ）管"内部信函"，档案柜（ MongoDB ）管"人事"，账房（ InfluxDB ）管"流水"。**每个编制只干自己最擅长的，这就是架构。** 上一篇那句话在这儿又应验了：搭 Broker 是拧螺丝，搭平台是编乐队。

顺带一个彩蛋。付强在书里写 Erlang 的变量不可变（"赋值"其实是解方程），写模式匹配多优雅，最后忍不住来一句："**Erlang 让我第一次有写程序犹如在写诗的感觉。**"

我常把这句话念给学生听。一个 1987 年为电话交换机生的语言，三十多年后成了物联网基础设施的骨架——**没有白学的技术，只有还没到花期的技术。**

## 六、一次"等电话等来事故"的实训

去年一个小组做实验室监控，用了轮询（就是彭老师当年那个办法）。演示当天，他们在项目报告里写"系统实时性 < 1 秒"，现场一测——平均延迟 8 秒。

原因就在轮询间隔上：间隔设小了，后端 CPU 飙红；设大了，延迟上去了。**"打电话问"这个姿势，本身就卡在成本和时效的拉锯战里。**

改成 Webhook 后，消息从设备到后端是"推"的，延迟降到 200 毫秒以内， CPU 反而降了。

验收答辩时评委问："你们的优化思路是什么？"学生答了一句我备课都没备过的话：

**"我们把系统从'主动打听'改成了'守株待兔'——准确地说，是让事件来敲门。"**

我后来想，这个"等电话来"的故事，其实是整个系列一直在讲的那条环的微缩版：**感知（事件发生）→ 传输（呼你）→ 决策（后端处理）→ 执行（下发/告警）→ 再感知（确认）。** 连"知道"这个动作本身，都得挂在环上。

## 七、一点"为什么这么想"的思考

三篇"平台内功"写到这儿，可以收个总了。

回头看：**中间件**是物业公司，**协议**是公司的语言体系，**Webhook** 是公司内部"谁主动"的规矩。这三样，是教程里最不爱写、生产里最要命的东西。因为它们不酷——没有跑马灯，没有" Hello World 五分钟上手"；但它们决定了你的系统**能不能从 demo 长成产品**。

我特别想说的一个体会：付强这本书，通篇没有"颠覆式创新"，全是开源软件的组装——EMQ X、 MongoDB、 Redis、 Node.js、 RabbitMQ、 InfluxDB。但就是这个"组装"，把"一万台设备"这个看似要航母编队才能搞定的事，变成了一群免费开源软件的合奏。

**工程能力的本质，很多时候不是"从零发明"，而是"知道有什么、放在哪、怎么接"。** 这跟作曲一个理：音符就那么多，曲式各有规矩，难的是知道在第七小节，让哪件乐器进。

至此，"白话物联网"这个系列，从"物是什么"讲到"平台的里里外外"，二十来篇，那条环算是从头到尾走了一遍：

物 → 五官 → 神经 → 普通话 → 总调度 → 邮局 → 档案 → 账房 → 脸面 → 免疫 → 空间感……

环还是那条环。但希望你再看它时，眼里不只是一个圈——**是一整套编制、一整套语言、一整套"谁主动"的规矩，在比特和原子之间，日日夜夜地闭环。**

哪天你想动手搭一个自己的"物业公司"，照着这三篇的目录去装，够了。
