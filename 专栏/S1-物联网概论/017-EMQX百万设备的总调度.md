# EMQ X：百万设备挤上来，谁来当这个"指挥"

## 一、我当年的困惑

讲完 MQTT，学生必问一个问题：

> "老师，设备直接往服务器发不就完了，中间非要有个 Broker 干嘛？多此一举？"

我当年也这么想过。一个温度计，一个服务器，俩组件直连，多干净。直到做第一个"设备稍多一点"的项目，才知道自己多天真。

## 二、一台设备是直连，一万台就是灾难

一个设备直连服务器，确实干净。

一万个呢？你想想服务器要遭多少罪：

- 一万条连接全挂在它身上，内存、端口、线程，全被这万个"常驻户口"占满；
- 设备张三李四王五，各说各话，有的发 JSON，有的发裸数字，服务器得挨个翻译；
- 谁掉线了、谁在重连、谁的消息漏发了——这些破事，全得服务器操心；
- 后端有十个应用都想用这份数据，是让每个应用自己连一万个设备，还是……

发现没？**设备一多，"谁来管连接、谁来翻译、谁来调度"就成了要命的问题。** 让干业务的应用去管这个，就像让外科大夫去管挂号——不是不能干，是离谱。

于是就有了 Broker 这个专门的角色。

## 三、Broker：快递柜大爷，一人干四件事

Broker（代理/中转站）的定位，就是那个快递柜大爷。设备和应用都只跟他打交道，彼此不见面。他一个人包圆四件事：

1. **扛连接**：百万设备同时在线，他扛着。应用只管来取数据，不用直面百万连接；
2. **当翻译**：设备说啥方言他都接得住，统一整理成应用能用的样子；
3. **做调度**：谁订阅了哪个主题，消息来了往哪投递，他门儿清；
4. **管死活**：谁掉线了、谁的遗嘱该广播了、谁的消息要补发——这些脏活他全包。

**应用世界因此被解放了**：写 App 的程序员，不用懂单片机；搞设备的工程师，不用管后端。两边隔着 Broker，各干各的。这份"解耦"，就是中间件的全部价值。

## 四、EMQ X：咱中国人自己的快递柜大爷

Broker 这活儿，最有名的开源选手之一，就是 **EMQ X**——国产的，Erlang 写的，天生就是为"百万并发"这个硬指标生的。

它的本事，三个字：**扛、稳、全**。

- **扛**：单集群百万连接起步，电信运营商级别的量；
- **稳**：分布式集群，一台挂了别的顶上来，7×24 不歇气；
- **全**：MQTT 全家桶（三种 QoS、遗嘱、保留消息）支持得规规矩矩，还带规则引擎——数据流进来，可以按规矩分流：存数据库的存数据库，触发报警的触发报警。

我为啥课堂实战选它？三个实在理由：国产（心里踏实）、开源（不要钱）、文档全（学生自学不卡壳）。配合 IotHub 那套后台（Node.js + MongoDB + Redis + InfluxDB），就是一套完整的"设备—Broker—云平台—手机"全链路。学生跑通这一套，简历上就能写"物联网平台开发经验"。

## 五、一个"没有指挥"的翻车现场

早年间带学生做个"宿舍用电监测"，二十个屋，每个屋一个电表模块，直连后端服务器。

头两周挺好。第三周开始，诡异的事情来了：数据时有时无，重启就好，过半天又犯。查了一星期，病因让人哭笑不得：

- 二十个模块，断线重连全挤在同一秒（模块一起上电）；
- 后端没有 Broker，每个模块一条裸 TCP 连接，谁掉线了后端根本不知道；
- 模块一掉线，它采的数据就永久丢失——没有任何"遗嘱"机制通知后端"我挂了"。

二十个设备尚且如此，你敢想象二十万个？

后来换上 EMQ X：连接它管、重连它管、遗嘱它管、消息分发它管。后端代码删了一半，稳定性反而上去了。学生看完只说了一句：**"原来中间这个大爷，是替我们受罪的。"**

## 六、一点"为什么这么想"的思考

中间件这东西，是典型的"平时看不见，缺了要人命"。

它的哲学，说白了就一句：**把"麻烦的连接"收到自己肚子里，把"干净的秩序"递给应用。** 这跟城市的地下管网一个道理——没人夸下水道，可没有它，城市一个月就瘫。

学物联网到这一层，你会慢慢品出一个规律：**越是庞大的系统，越要靠中间层"受罪"。** 操作系统受内存调度的罪，数据库受并发一致的罪，Broker 受百万连接的罪——正因为有它们在前面扛，后面的应用才能写得那么云淡风轻。

看懂"受罪层"，你就看懂了大型系统的一半。
