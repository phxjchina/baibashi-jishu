# MQTT：物联网的普通话，是怎么"炼"成的

## 一、我当年的困惑

数据通过神经传到云端了，接下来的问题是：**设备跟平台之间，说什么话？**

我当年的困惑特别具体：HTTP 用得好好的，浏览器跟服务器聊了三十年，物联网干嘛非要另起炉灶，搞出个 MQTT？

这篇就把这事说透。MQTT 的地位，行话叫"物联网的普通话"——几乎是个物联网设备就会说。它凭啥？

## 二、先回忆快递柜：MQTT 的全部就这三句

上一篇做过温湿度上云，其实你已经用过 MQTT 了。它的规矩，快递柜那套就够：

- **Broker 是快递柜**，谁的数据都往这搁；
- **主题（topic）是柜子编号**，比如 `mylab/temperature`；
- **发布是投快递**，**订阅是凭号取件**。投的取的互不认识，只认编号。

就这三句，没别的。那它比 HTTP 强在哪？三个字：**短、喊、扛。**

## 三、强在哪一：短——报个数，俩字节就够

HTTP 你是见识过的：一个请求，请求头、请求体、Cookie、UA……啰里啰嗦几百字节，里头真正干活的（比如"26.5"这个数）可能就几个字符。

MQTT 不搞这套虚的。它的报文精简到骨感：发一条温度，**有效载荷俩字节**，开销极小。

这为啥要命？俩场景：

- 设备用的是流量卡、卫星链路，每字节都花钱——短，就是省钱；
- 设备是电池供电，发射无线电巨费电——发得少，就是续命。

**为受限设备生的协议，第一美德就是省。**

## 四、强在哪二：喊——不用挨个问

HTTP 是"请求-响应"：你想知道温度，你得问一句"现在几度"，设备答一句。十个用户想知道，设备就得被问十遍。

MQTT 是"发布-订阅"：设备把温度往 Broker 一"喊"就算完，谁爱听谁订阅。一个人听、一万个人听，**设备的负担一点不加**。

这个差别，在设备一多时要命。一个工厂十万台设备，要是都按 HTTP 那个"挨个问"的来，平台早被问趴了。用"喊"的，设备喊完就睡，谁来听它管不着。

**一个喊、随便听，这才是海量设备的处方式。**

## 五、强在哪三：扛——皮实，断线了自己爬

设备上网，不比你的手机——它可能进电梯、穿山洞、电池没电。HTTP 那套"一问一答"一断就傻眼，而 MQTT 天生就是为这种烂连接设计的：

- **断线重连**：掉了，自动接回来，接着喊；
- **遗嘱消息（Will）**：设备连上时先留句"遗言"——"我要是半路掉线，请替我广播一声'我挂了'"。设备猝死，Broker 帮它发讣告，后端立刻知道"这货掉线了"，不用干等；
- **保留消息**：最新一条数据 Broker 替你存着，谁新来订阅，先把旧账给他看，不用干等下次更新。

这三招，全是冲着"设备世界网络烂、会掉线、会猝死"去的。**HTTP 是给人用的协议，人断线会自己刷新；MQTT 是给物用的协议，物没人伺候，协议得比人更周到。**

## 六、报温度，到底用多"可靠"？QoS 三档

MQTT 还有个贴心的设计：**送快递，三种送法，你按需选。**

| 档次 | 白话 | 适合啥 |
| --- | --- | --- |
| QoS 0 | 扔进柜就算，到没到不管 | 温度湿度，丢一条无所谓 |
| QoS 1 | 保证送到，不到重发 | 报警、指令，不能丢 |
| QoS 2 | 亲手交到你手里，还要回执 | 支付、门禁指令，一次都不能错 |

学生常问："那我全用最高档不完了？"——不行。**可靠是拿速度和流量换的。** 报温度用 QoS 2，等于寄平信用顺丰冷链，穷讲究。

按数据的"重要性"选档，又是一道取舍题。

## 七、一点"为什么这么想"的思考

为什么一个"快递柜"式的简单设计，能成物联网的普通话？

我常跟学生说：**因为 MQTT 看清了设备世界的三个真相——话费贵（所以短）、嘴不够用（所以喊）、命不长（所以皮实）。** 它不是技术更高级，它是更懂"物"的处境。HTTP 服务的是"坐在电脑前的人"，MQTT 服务的是"挂在电线杆上、埋在田里、漂在水上的物"。

协议这东西，没有先进落后，只有**懂不懂用户**。这道理，放在哪都成立。
